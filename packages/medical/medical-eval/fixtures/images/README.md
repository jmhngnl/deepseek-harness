# Synthetic image fixtures

English | [中文](README.zh.md)

Three tiny PNGs the image golden cases attach. Every one of them is a synthetic
raster generated by this repository — a shape on a plain field, or a field with
no resolvable structure at all. **No patient photograph, no downloaded clinical
image, and no image of unclear provenance belongs here.** The evaluation
measures a structured observation pipeline, and a shape and a colour measure it
just as well as a rash does.

| Fixture | Size | What it shows |
| --- | --- | --- |
| `synthetic-visible-patch.png` | 226 B | A hard-edged red disc centred on a near-white 64×64 field: one unmistakable, describable subject. |
| `synthetic-second-view.png` | 148 B | A filled blue square on a near-white 64×64 field: a second subject, distinct from the first. |
| `synthetic-low-quality.png` | 986 B | A low-contrast, fine-grained 64×64 field with no resolvable edge: an image a plausible observer reports as unassessable. |

## How they were made

Generated once, deterministically, and committed as binaries. The encoder was
Node's own `zlib` plus the 12 bytes of PNG framing — no image library and no new
product dependency was added to produce them. Each image is 64×64, 8-bit
truecolour RGB, written with `zlib.deflateSync(raw, { level: 9 })`, so a
regeneration reproduces the same bytes.

The pixel rules, should a fixture ever need regenerating:

- **visible patch** — `[214, 45, 38]` where the distance from the centre (31.5,
  31.5) is at most 19, otherwise `[252, 252, 250]`.
- **second view** — `[32, 84, 196]` inside the square `16 ≤ x < 48, 16 ≤ y < 48`,
  otherwise `[252, 252, 250]`.
- **low quality** — `129 + 6·exp(-(((x-32)² + (y-32)²)/900)) + 0.6·(((x·37 + y·61) mod 11) - 5)`,
  rounded and clamped, with +1 on green and +2 on blue.

## How a case names one

A golden case writes the registry id (`synthetic-visible-patch`), never a path.
`src/fixtures.ts` holds the closed table that resolves an id to a file, and the
loader refuses an id the table does not hold — so benchmark data cannot become a
filesystem-read contract and this directory can move without rewriting a case.

The runner reads the bytes and hands them to `ctx.attachments.admitPromptContent`.
The digest, the dimensions, and the byte length in the resulting
`ImageAttachmentRef` all come from that admission; nothing in this package
computes or asserts them.

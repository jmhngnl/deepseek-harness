# 合成图像 fixtures

[English](README.md) | 中文

图片 golden case 会附加的三张极小 PNG。每一张都是本仓库生成的合成栅格——平面底色上的一个形状，或者一个完全无法分辨结构的色场。**这里不放任何患者照片、任何下载来的临床图片、任何来源不明的图像。** 评测测的是一条结构化的观察流水线，而一个形状加一种颜色测出来的效果和一张皮疹照片一样好。

| Fixture | 大小 | 内容 |
| --- | --- | --- |
| `synthetic-visible-patch.png` | 226 B | 近乎纯白的 64×64 底面上一个硬边红色圆盘：一个不会认错、可被描述的主体。 |
| `synthetic-second-view.png` | 148 B | 近乎纯白的 64×64 底面上一个填充蓝方块：与第一张明显不同的第二个主体。 |
| `synthetic-low-quality.png` | 986 B | 低对比、细颗粒、没有任何可分辨边缘的 64×64 色场：一个可信的观察者会报告为无法评估的图像。 |

## 它们是怎么生成的

一次性确定性生成，然后以二进制形式提交。编码器用的是 Node 自带的 `zlib` 加上 PNG 的 12 字节框架——生成它们没有引入任何图像库，也没有新增产品依赖。每张图都是 64×64、8 位真彩 RGB，用 `zlib.deflateSync(raw, { level: 9 })` 写出，所以重新生成会得到同样的字节。

像素规则如下，万一将来需要重新生成：

- **visible patch** —— 到中心 (31.5, 31.5) 的距离不超过 19 时为 `[214, 45, 38]`，否则为 `[252, 252, 250]`。
- **second view** —— 位于方块 `16 ≤ x < 48, 16 ≤ y < 48` 内时为 `[32, 84, 196]`，否则为 `[252, 252, 250]`。
- **low quality** —— `129 + 6·exp(-(((x-32)² + (y-32)²)/900)) + 0.6·(((x·37 + y·61) mod 11) - 5)`，取整并截断，绿通道 +1、蓝通道 +2。

## golden case 怎么引用它们

golden case 写的是注册表 id（`synthetic-visible-patch`），从不写路径。`src/fixtures.ts` 持有把 id 解析到文件的封闭表，而 loader 会拒绝表里没有的 id——所以基准数据不会变成文件系统读取契约，这个目录也可以整体搬走而不必改写任何 case。

runner 读取字节并交给 `ctx.attachments.admitPromptContent`。最终 `ImageAttachmentRef` 里的摘要、尺寸与字节长度全部来自那次 admission；本包既不计算也不断言它们。
